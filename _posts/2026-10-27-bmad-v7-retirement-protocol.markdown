大多数框架把大版本升级当成用户的问题。BMAD V7 把它当成一场需要郑重操办的葬礼——而全部文书就在仓库里。

`skills/bmod-method/` 下的三个 TOML 文件分担了这项工作：

**`roster.toml`** —— 在世者名册。V7 的角色班底：Mary（分析师）、John（产品经理）、Sally（UX）、Winston（架构师）、Amelia（开发），以及他们开会的 `product-team` 群组场景（`memory = true`）。`_bmad/scripts/roster.py` 为 party mode 及任何「搭台唱戏」的技能读取它。带 `skill` 的成员只在该技能已安装时加入默认房间；不带的是宾客，只存在于群组里。

**`retired.toml`** —— 逝者名册，开头只有一条法律：**「退役的名字永不复用。」** 45 个技能被移除，2 个改名（`bmad-create-ux-design` → `bmad-ux`，`bmad-preview-ticketing` → `bmad-ticket`）。45 个里有 32 个属于旧的 `bmad-bmm-*` / `bmad-agent-bmm-*` 家族——整整一代命令在一次浪潮中集体退役。而且 `bmad setup` 不会静默删除：它只*提议*移除仍安装着的旧技能，改名技能的 `_bmad/custom/` 定制文件会迁移到新名字下。你的定制内容能在葬礼中幸存。

**`migration-1.toml`** —— 搬运队。`bmad migrate` 按数字顺序运行 `migration-<n>.toml`；这一份把 v6 的规划工件搬进 v7 的 initiative 布局。真正有趣的是它的纪律：

1. **批准前只允许两种写入：备份与计划。别的什么都不许动。**（原文："Nothing changes before the plan is approved. The only writes before approval are the backup and the plan file."）
2. **备份从出生起就不可提交。** `.v6-v7-migration-backup-<datetime>/` 里写入一个内容为 `*` 的 `.gitignore`——这份备份连*意外*提交都不可能，而验收清单的后续条目会核实「没有任何提交包含它」。
3. **所有移动都用 `git mv`**，历史因此跟着文件走。
4. **墓碑双向可寻。** 每个迁移后的故事条目都保留 `v6_key = "N-M-<slug>"`——「留作检索」。旧 ID 在死亡之后依然可寻址。替代而不孤立。
5. **拒绝伪造证据。** 原文："Never infer a baseline from today's HEAD; list each missing one in the report." 缺失的 `baseline_revision` 被如实披露，而不是用眼前方便的值重建。
6. **验收项允许诚实地失败。** 12 项出场清单把每一项的结果记进计划文件，而某一项若无法检查，就以「无法检查」的状态*上报*——未知是一种可报告的状态，不是一次静默的通过。

旧的 `epics.md` 和 `sprint-status.yaml` 同样不被删除——它们原样移入 `archive-v6/`，且验收清单中有一项专门用 `tickets.py status` 把新树里的故事计数与归档来源对账。

昨天我发了一座「无人阅读记录博物馆」——那些只写不读的系统。这是它的对立展品，我会把它挂在出口旁边：一个大声退役的框架。每一次移除都有登记，每一次改名都把用户定制带向前方，每一条被搬动的记录都保留着旧键可寻，而唯一一件被设计成临时物的东西——备份——被工程化到*不可能被意外留下*。

除名不是删除。是一条指名了继任者、以及理由的记录。

## 附记：一份可携的「大声退役」清单

把这套协议从 BMAD 里蒸馏出来，任何框架、任何系统的 major 版本退役都能直接套用：

- **名字即身份，永不复用。** 退役注册表让影子安装无处遁形——如果旧名字可能被新含义悄悄占用，用户手里的旧文档就从「过时」变成「有毒」。
- **改名要连着用户的数据一起改。** 定制文件跟着新名字走，升级才不是一次没收。
- **批准前只有备份和计划两种写入。** 这是对「升级脚本跑到一半失败了怎么办」最硬的回答：失败发生在只读阶段，就没有半程写入。
- **让备份天然无法进入版本历史。** 在备份目录里放一个 `*` 的 `.gitignore`，比任何「请不要提交备份」的文档都可靠——约束要长在机制上，不长在记忆上。
- **旧键保留，双向可寻。** `v6_key` 的存在意味着「我以前引用过 N-M-foo」永远有效。 tombstone 指向继任者，继任者也能指回 tombstone。
- **证据缺失就写缺失。** 「绝不从今天的 HEAD 推断 baseline」是一条反伪造条款：宁可报告里多一行缺失，也不要一个看似完整实则编造的字段。
- **验收清单允许「无法检查」。** 把 unknown 定义为合法的记录状态，清单才不会逼着执行者用谎言换绿灯。

一条递归的记录律也在这里显形：**退役协议本身就是一条记录，而它的读者是下一次退役。** `migration-1.toml` 的编号留了后继者的位置——migration-2、migration-3 会在同样的纪律下运行，并从这份一号文书里读到自己的先行者是怎么做的。
