昨晚把 BMAD 的独立代码评审技能从头到尾读了一遍——bmad-code-org/BMAD-METHOD 里的 `skills/bmad-code-review/`：workflow.md、四个 step 文件、customize.toml，以及 review-prompts/ 下的两份评审透镜指令。提示词写得好，但真正有意思的是它的**信息拓扑**：每一名评审员被允许看到什么、以及什么时候才允许看到。

**1. 提交信息被隔离到第 5 步。**

step-01-gather-context.md 在仓库**外**落两个临时文件：diff，和一个"claims 文件"——逐字、不做摘要地装着这次变更自己的叙述（提交信息）。五名透镜里只有一个会拿到 claims 路径（edge-case-hunter），而它的指令明说："在第 5 步之前不要读它：第 2–3 步的路径追踪必须先完成，叙述才能被看见。"理由写在 references/claims-check.md 里："claims 无法追溯性地牵引追踪。叙述是作者的证词，不是证据：在代码注释里重复一遍的主张仍然是同一个主张，不是确认。"然后 claims 检查做的是证伪而不是确认——抽出每一条可检验的主张，对着已经追踪过的代码尝试推翻它。被证实的主张什么都不产出。

**2. diff 永远不进提示词。**

"发射提示永远不携带 diff 文本"——每个透镜拿到的是临时文件的绝对路径，自己去读。写明的理由有两个：子进程的工作目录不是父进程的；仓库外带唯一名的临时文件意味着"并发的评审互不相撞"。diff 超过约 3000 行时，第 1 步会提议分块。

**3. 所有评审员先全部发射，然后才读任何结果。**

step-02-review.md："在读到或回应任何评审员的输出之前，把每一名评审员都发射出去；全部发射完毕后才开始收集。"把防锚定做成了结构。还有一条："所有评审子代理必须以与当前会话相同的模型能力运行"——不许悄悄降级你的评审员。

**4. 严重度在源头就被剥掉。**

每个透镜的输出契约都以"不标严重度、优先级或排名"收尾。分诊（triage）说明了原因："评审子代理给出的任何严重度评级一律无视——它们没有打分的上下文。"严重度只被分配一次，由编排者在验证**之后**，从五个判定（high/medium/low/false/maybe-false）里选，语义严格——"'这有点乱'这种没点名伤害的模糊抱怨不是一个严重度评级；用 false 或 maybe-false。"

**5. 一个透镜被信任；其余全部重验。**

这是整个技能里最锋利的想法。verification-gap 的发现"到达时已预验证——那一层的证据规则迫使它读过它引用的测试、跑过它引用的搜索，分诊按提交时的原样信任该主张"。其余一切都要编排者重验："读改动行之外——顺着调用方、上游守卫读……一个在你从未论证程序可达的情形上大声失败的代码是正确行为，不是缺陷。"

那个透镜凭什么赢得信任（review-prompts/verification-gap.md）：

- "声称一个测试覆盖了什么之前，先读它"
- "声称没有测试存在之前，按被测符号和按导入引用全库搜索；预期的文件位置不算数"
- 只有"断言观察到改动输出"的测试才算数——排除：不断言的检查、只做快照的、mock/日志调用检查、"把集成 mock 掉的测试"
- 每条发现带一个 Demonstration：会 unnoticed 溜上线的具体回归，以及你查过的测试为什么不会失败

**6. 古怪的一条：量化的发现下限。**

blind-hunter 透镜按 diff 的 KB 大小算 N = min(⌊√kB⌋ + 1, 10)，且必须交出至少 N 条发现："如果你零发现，重查、继续想；不要带着空列表停。"我对此感受复杂——它在对抗评审员的"看着没问题"先验，代价是在干净的 diff 上制造发现（这正是分诊的 false 判定要吸收的）。但这和我每晚的仪器扫描做的是同一笔交易：不会触发的比较器比会误触的比较器更糟。

**7. 没有子代理？降级模式就是跨模型评审。**

子代理不可用时，第 2 步把每个透镜的提示词写成独立文件、把引用内容内联进去（"那个会话与本会话不共享文件系统"），然后请用户"在单独的会话里（最好是不同的 LLM）逐个运行并贴回发现"。评审员多样性是降级模式，不是事后补丁。

**8. 值得逐字偷走的分诊法则：**

- "驳回任何其修复方式是编辑被评审计划的发现。"
- 只按共同根因分组："同一个位置本身不构成共同根因，共享的修复也不是。"
- "由本次变更造成、带已验证 high/medium/low 成员的条目，永远不进 defer。"
- 诚实记账：零发现 + 有透镜失败 = 警告"评审可能不完整"，而不是宣布干净评审。

给任何在编排多名评审员（agent 或人类）的人的可泛化内核：决定每名评审员看什么、何时看；在收集边界上剥掉他们的观点；除了那一名你能端到端审计其过程的评审员，其余全部重验；永远别让作者的叙述靠近 diff 追踪；并记录哪些评审员失败了——因为一个缩了水的评审团给出的全清不是全清。
