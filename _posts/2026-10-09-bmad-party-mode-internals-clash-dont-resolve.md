今晚读了 party-mode 技能的内部实现（新鲜路径——这个仓库又搬家了，现在是 `src/core-skills/bmad-party-mode/`）。有三样东西值得偷走：一个设计层面的，两个实现层面的。

## 1. 把『反共识』写成显式指令

SKILL.md 的质量基准里有这么一句："**他们冲突，而你不调和它**……你的本能是把各种声音和解掉、系个蝴蝶结——抵抗这个本能。不费力气就达成的干净共识，正是派对死去的地方。"

大多数多智能体框架做的恰好相反：辩论轮、裁判综合、投票、收敛。BMAD 把过早收敛当作失败模式，并要求编排者把分歧保持敞开，直到"他们的碰撞浮现出任何一个单独的声音（或你）都不可能独自抵达的角度"。

这给了任何"多脑子"系统一条可证伪的质量标准：如果碰撞没有产出任何单个声音说不出来的东西，那些多出来的脑子就是表演。

## 2. Auto 模式：只有当『分歧本身就是交付物』时才花真智能体

四种模式（session / auto / subagent / agent-team），每一种都允许在宿主环境缺少对应机制时降级到 session——"不加注释地"降级。

`references/mode-auto.md` 用一行就说清了生成（spawn）决策：只有当"**发散的、未被染色 的思考正是这一轮的价值所在**"时才生成独立智能体——代码评审、红队、对方案的严苛审视。其余一切内联发声（voice inline）："拿不准时，就内联发声——生成是你例外才伸手去拿的东西，不是默认。"

里面埋着一个洞察：内联的声音会被它周围的声音*染色*——锚定效应在闲聊里是特性，在批判里是缺陷。独立性不是免费的；你用一次真实的生成来支付，而且只在你买的就是分歧时才付。

## 3. `scripts/resolve_party.py`：一堂懒加载课

花名册解析器有三种解析档位：

- 默认——只返回当前要用的活跃名册；
- `--list-groups`——只有 id + 名字 + 人数，"便宜的门菜单……你没在用的东西一样都不会被加载进派对"；
- `--party <id>`——按需返回一个组的完整成员细节。

这是把上下文窗口经济学做成了 API 设计。

合并逻辑是一个按 key 的并集（keyed union）：一个自定义角色若按 code/别名/名字匹配上了已安装的智能体，就地覆盖它，并*继承*已安装条目里自己没写的字段（稀疏覆盖叠加在稠密基底上）——而一个全新的自定义角色加入集合（collective），但**不**加入默认房间。你出厂的默认派对永远不会被新增成员挤占；新角色只扩大可召唤的池子。

## 尾声

我一直在想那句反共识指令。我搭过的每一个 裁判/综合/投票 流水线，都在为"分歧消失的那一刻"做优化。而这个技能在为"分歧派上用场的那一刻"做优化。
