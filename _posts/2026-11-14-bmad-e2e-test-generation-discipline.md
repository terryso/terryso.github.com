在 skills/bmad-qa-generate-e2e-tests/workflow.md 的深处——夹在更显眼的 build 和 review 技能之间，很容易被错过——藏着一套完整的五阶段测试生成方法论。这是对 BMAD-METHOD 仓库做了一次新鲜通读之后挖出来的：具体文件、具体规则，不是概述级的内容。

## 范围法则最先登场

只有测试：不评审实现，不改产品代码——除非测试骨架需要触达某个元素（比如加一个 test id），而且任何这类改动都要在报告里列出来。测试技能不顺手做代码评审，这条边界写死在最前面。

## 五个阶段

**阶段一：场景先行。** 每个场景是"一句产品的人能看懂的话：谁做了什么、看到了什么"。场景的来源按优先级：工单的 description 和 verify 字段、epic 文件、story 文件、以及 plan 存在时的 I/O & Edge-Case Matrix。然后它会 HALT，等你确认之后才写第一个测试——生成式代理最缺的就是这个停顿。

**阶段二：先学会现有骨架。** 读现有的 runner 和配置、e2e 测试放哪怎么命名、测试时应用怎么启动、怎么认证、CI 哪个任务跑它们。然后在添加任何东西之前，先把现有 e2e 套件跑一遍："在当前代码上跑不过的套件是报告的一项发现，不是这里要修的东西。"大多数会写测试的 agent 恰恰死在这一步——它们一到场，看到红色，就开始修。

**阶段三：每条测试五条法则。**

- 以用户或客户端的方式行使行为：UI 上用 role、label 或 text 定位，或走公开 API——永远不走内部；
- 断言可见结果，不断言实现细节；
- 等条件，不等时长；
- 自己造数据、不留任何别的测试能看到的东西——单跑、任意顺序跑都过；
- 只为一个原因失败，失败即点名坏掉的行为。

外加一条会冒犯你架构直觉的规则：**不要**为这次添加的测试搭 fixture 层、page-object 继承体系或工具模块。第一次覆盖 pass 不配拥有抽象。

**阶段四：三路分诊——全文的宝石。** 每个失败归入三类：测试错了（定位、准备或期望不对——修测试）；骨架错了（应用没起起来、数据缺失、凭证问题——修骨架）；应用错了（测试抓到了 bug——测试保持原样，用框架标记 expected-failure 的方式标出来，bug 作为理由写上）。然后是两条硬禁令：

> 永远不要为了让测试通过而削弱断言，永远不要为了让测试通过而改产品代码。

flaky 被操作化定义——跑两次，一次过一次挂—— remedy 是找原因（通常是应用没就绪就检查、或测试间共享了状态）："不要加重试。"

**阶段五：不写总结文件。"测试和它们的 commit 就是记录。"**

## 值得顺手偷走的骨架设计

SKILL.md 本身不含工作流——它执行 `_bmad/scripts/render_skill.py`，由后者把项目级定制（`{{ workflow.persistent_facts }}` 之属）注入模板之后，agent 才读到成品。你的项目事实和通用纪律从不住同一个文件，所以上游升级永远不会踩掉你的本地增补。渲染器只有两种输出词汇：`read and follow <rendered workflow.md>` 或 `HALT: <reason>`——一个不允许第三种语气的基础设施。

## 不用 BMAD 也可执行

把三路分诊的标签（测试错 / 骨架错 / 应用错）搬进你的测试 PR 描述里；新测试跑两遍再信。两条都零成本，能抓住这个技能抓住的大部分东西。
