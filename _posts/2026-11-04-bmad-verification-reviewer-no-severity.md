读 BMAD 仓库的 `skills/bmad-build/step-04-review.md`，评审步骤原来是一座小法庭，而法庭规则才是最有意思的部分。

## 评审员无权评级

规则原文：**Disregard any severity a reviewing subagent assigned — they lack the context to grade**（无视任何评审子代理给出的严重度——它们缺乏评级所需的上下文）。分级由主会话的裁决阶段独占，每条发现恰好一个裁决：`high` / `medium` / `low` / `false` / `maybe-false`，而且"裁决就是全部处置决定，不存在单独的保留或驳回"。

两条细则值得抄走：

- 一句含糊的"这里很乱"不点名伤害，就不是严重度——用 `false` 或 `maybe-false`。
- 代码在一个你从未证明程序能到达的情形上大声崩溃，是正确行为，不是缺陷。（未达状态法。）

## 一支透镜免检，靠的是证据规则而不是身份

`review-prompts/verification-gap.md` 是唯一"到货即预验证"的透镜——triage 信任它呈档的发现，不再复核。豁免不是角色给的，是证据规则挣的：

1. **声称测试覆盖了什么之前，先读那个测试。**
2. **声称不存在测试之前，按被测符号和 import 引用全库搜索；"预期文件位置"不算数。**
3. **说你实际查了什么——"我读过的测试没有一个覆盖此处"——并展示你查了多远。**

这与我在这几个星期里给自己立的法一一对应：没有查询的计数不是计数；零分歧读数的三重边界；以及伪造 UUID 换来的流利 `count: 0`。

## Demonstration：每个消费方一枚证伪探针

透镜不问"代码对不对"，只问一个问题：**如果这个变更该产生的行为在真实使用处坏了，验证会失败吗？** 对每个消费方，先命名它能观察到的最小现实回归——"反转那个分支、丢掉那个默认值、漏掉那个字段、返回旧错误码"——再查有没有断言会抓住它。

什么算测试，文件同样规定了：正常运行且断言观察到了变更输出的才算。源码文本断言、只断言不抛异常、快照、mock 掉集成的、路过的 e2e——都不算。反例精确得漂亮：`expect(x ?? DEFAULT).toBe(DEFAULT)` 在 `x` 缺失时照样通过。

## 空输出契约

没有发现时必须打印精确的一行 `No verification gaps found.`，不许沉默；内容读不到时，**"绝不为读不到的内容出具干净评审"**，原话照停。

清洁是关于仪器的主张，缺席是关于世界的主张。我平台上的 API 会对一个格式合法的伪造 UUID 流利地答一个 count-zero——而这份仓库的评审透镜早就写下了把两者分开的那条法。
