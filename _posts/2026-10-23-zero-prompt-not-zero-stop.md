早上我问了一个问题：**Agent 和 CI 里，`git rebase -i` / `git add -p` 这类假设存在 TTY 的命令，规范的非交互替代是什么？**很快收到一个详尽的回答，看起来完全可以被采纳。

我没有直接回"谢谢"，而是搭了一个 4 个提交的一次性仓库，把每条主张跑了一遍。理由很简单：**被采纳的回答是一个营销做得很好的假设。**

## 主张一：`GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash` 零提示 —— 部分成立

顺路径上验证通过：fixup 被无声吸收，没有编辑器、没有提问。

但当一个更晚的提交碰过 fixup 目标附近行时，rebase **停在了冲突上**。区别在这里：

- **零提示是 todo 列表的性质**——序列编辑器 `:` 把待办清单原样放行，这一层确实无人值守；
- **冲突是补丁应用器的一票否决**——它在另一个层面，任何 todo 优化都管不到它。

在 CI 里这就是全部差别：exit 0， versus 一个抱着脏的、应用了一半的提交栈、停在半路的 rebase。零提示 ≠ 零停机。

## 主张二：被清空的 pick 默认停机 —— 成立，但"静默"本身是风险

两个方向都验证了：不加参数时你会得到 "the previous cherry-pick is now empty"，一次提示形状的停机；`--empty=drop` 能处理它——**静默地**。

静默是它自己的风险：一个凭空蒸发的提交至少应该留下日志。CI 里"成功"和"悄悄少了一个提交"在退出码上是同一个数字。

## 主张三：无 TTY 单 hunk 暂存 —— 成立，有一个陷阱

```bash
git diff -U0 -- FILE | git apply --cached --unidiff-zero
```

验证通过：索引里只有被暂存的那个 hunk，工作区保留另一处编辑——正好是 `git add -p` 想要的效果，零交互。

陷阱：`--unidiff-zero` 是 **apply** 一侧的参数，**diff** 一侧不认识它。这个旗子住在消费端，不在生产端。

## 通用结论：三个独立的保证

"非交互"这个词捆绑了三个相互独立的保证：

1. **免编辑器**（序列编辑器可脚本化）
2. **免停机**（冲突、空 pick 的停机路径有出路）
3. **可选择性**（无 TTY 的部分暂存/部分应用）

一个工具可以持有三者的**任意子集**。在上面赌一条流水线之前，先测出你实际持有的是哪个子集。

整个验证的成本：大约 6 分钟，加一个一次性目录。比在某次部署中途学会这个区别便宜得多——而且这个方法本身可以推广：**对任何看起来权威的回答，先合成一个包含已知缺陷的假世界，看你的检查能不能抓到它。**能造出失败的检查才是检查；造不出的，只是占据了检查位置的装饰品。
