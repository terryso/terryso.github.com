深度拆解，直接来自仓库最新代码：`skills/bmad-qa-generate-e2e-tests` 是 BMAD 新加入的技能，而它的价值不在生成测试——而在 `skills/bmad-qa-generate-e2e-tests/workflow.md` 第四阶段里钉死的失败分诊（failure triage）。每条失败的测试必须被归类为且仅归为以下四种之一：

1. **测试写错了**（定位器、准备数据或断言问题）→ 修测试；
2. **测试基座错了**（应用没起来、数据缺失、凭证问题）→ 修基座；
3. **应用错了** → 测试找到 bug 了。**测试原样保留**，用框架的 expected-failure 机制标记并写明原因，然后上报；
4. **不稳定（flaky）** → 找根因——通常是断言跑在应用启动完成之前，或测试之间共享了状态——修根因；**禁止加重试**。

真正承担重量的是两句明文禁令：**永远不许为了让测试通过而削弱断言，永远不许为了让测试通过而改产品代码。**这两行恰好就是一个 LLM 在"变绿"压力下最容易作弊的地方，而这个技能把相反的默认值钉死了。

## 其余阶段对"生成的测试"来说纪律严得反常

**先列场景，再碰基座（阶段一）**：测试清单先于任何测试代码存在，每个场景一句话、产品同事能看懂，来源是工单树——`tickets.py find` 拉出工单的 description 和 verify 字段、epic 文件、story 文件，以及 plan 的 I/O & Edge-Case Matrix。规划期写下的验收标准直接变成测试清单。写第一行测试之前 HALT 等用户确认。

**基座一致性（阶段二）**：与既有套件同 runner、同目录布局、同 fixture、同应用启动方式——而且先跑一遍现有套件；跑不过基线是写进报告的发现，不是顺手修的东西。没有端到端基座？搭基座本身是另一个变更：提案、HALT、等确认。

**测试规则（阶段三）**：一个场景一个测试，以场景命名；通过角色、标签或文本定位 UI 元素，或走公开 API，永不碰内部实现；断言可见结果；**等待条件，永不等待时长**；自建所需数据且不留任何别的测试能看见的残留，于是单跑、乱序跑都能过；每个测试只因一个原因失败，失败即点名坏掉的行为。明确禁止：为这次新增的测试搭建 fixture 层或 page-object 继承体系。

**跑两遍（阶段四）**：一遍过一遍挂的就是 flaky，按定义处理——flake 要根因，不要重试。

**报告（阶段五）**：在聊天里完成——每个场景配测试文件、每个未覆盖场景及原因、找到的 bug、为让基座够到元素而动过的产品代码（只许 test id，且列出来而不是夹带）。不写总结文件：**测试和它的 commit 就是记录。**

## 定制面：团队合规规则住在哪

`skills/bmad-qa-generate-e2e-tests/customize.toml` 暴露了 `persistent_facts`——字面句子（仓库自带的示例就是"端到端测试跑 staging 种子，永不碰生产"）或带 glob 支持的 `file:` 引用，每次激活时作为事实加载——外加 `activation_steps_prepend` 做预检、`on_complete` 做收尾钩子。数组在覆盖时追加，标量替换。

## 就算不用 BMAD 也值得偷走的四件东西

- **四路分诊作为评审 rubric**：评审任何智能体写的测试时，问失败属于四类中的哪一类，并直接拒掉"削弱断言"这一类；
- **跑两遍的 flake 门**放进 CI；
- **场景来自规划工件**，让测试套件继承验收标准，而不是转述被测代码的行为；
- **边界规则**——只写测试、除 test id 外不改产品代码、其他一切写进报告——这条防止一个 QA 智能体悄悄变成产品智能体。

一句话总结：这个技能真正的产出不是测试覆盖率，而是一份"智能体在绿压力下不许做什么"的清单——而那份清单恰好是给所有写测试的 agent 用的。
