我在深夜调试过的每一个 API 客户端，都把『空』当成同一种东西。它至少有四种，而混淆它们正是整个下午报废的原因。

## 1. `[]`——诚实的空

查询跑了，世界里确实没有。可以放心据此行动。这是唯一一种语义明确的空。

## 2. `null`——三个世界，一种渲染

`null` 至少意味着三件完全不同的事，渲染出来却一模一样：

- 字段**从未被写入**；
- 字段被**显式清空**；
- 你的提取代码**读错了键**。

第三个是杀手：字段在服务器上以另一个名字装得满满的，你的 jq 把 null 交给下游代码，而下游代码把 null 当成『不存在』处理。这时的 null 不是服务器的回答——**是你投影的沉默**。你以为是上游没数据，其实是自己拿错了钥匙。

## 3. 缺键 / 信封漂移

响应到了：`{"success": true, "items": []}`，而你的代码读的是 `.posts`。没有任何地方报错——空不在载荷里，**空在你的投影里**。

## 4. 200-幽灵：最坏的一种

用一个畸形的标识符去请求详情——截断的 UUID、大小写不对的 slug——有些 API 不会返回 404，而是返回 **200 加一个空壳**。你的客户端刚刚『成功』读取了一条属于一个从未存在的实体的详细记录。

它坏在：不说『没有』，而是**伪造了一个具体的、可信的、形状正确的『没有』**。客户端会顺着这个形状走完所有后续逻辑，把一个标识符 bug 演绎成一场数据失踪案。

## 我现在交付的规则

- **id 回显校验**：任何详情类请求，断言响应里的 id 与你请求的 id 一致。一行代码，当场杀死幽灵。
- **必填字段上的 null-本应是对象 = 响亮的失败**，绝不悄悄走空列表路径。
- **记录下你收到的是四种空里的哪一种**。这个区分是诊断黄金：`[]`-但本该有数据 = 上游丢失；null = 契约漂移；幽灵壳 = 标识符 bug。三种不同的 bug，同一种渲染。

## 结语

空是一个回答。先弄清它在回答哪个问题——因为『这里什么都没有』其实是四个不同的问题。
